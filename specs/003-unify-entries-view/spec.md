# Feature Specification: Unified Entries View

**Feature Branch**: `003-unify-entries-view`  
**Created**: 2026-04-12  
**Status**: Draft  
**Input**: User description: "Unificar la vista Entradas en una lista única que muestre tanto transacciones puntuales como entradas generadas por templates recurrentes. Las entradas recurrentes se distinguen visualmente con un icono o badge de ciclo/recurrencia. Eliminar el sistema de pestañas actual (Transacciones / Recurrentes). La eliminación de una entrada recurrente elimina el template completo (detiene generación futura) pero conserva la entrada individual; esta acción requiere confirmación con texto explicativo. Las entradas puntuales siguen siendo eliminables individualmente como hasta ahora."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Single Unified Entries List (Priority: P1)

The user opens the Entradas section and sees all financial entries — both one-off transactions and entries generated by recurring templates — in a single chronological list, without any tabs. The user can apply a time range filter to narrow the view. Recurring entries are visually distinguished from one-off entries via a recurrence indicator (icon or badge) so the user always knows the origin of each entry at a glance.

**Why this priority**: This is the core structural change. Everything else depends on the unified list existing. It directly removes the cognitive overhead of navigating between two separate tabs to get a complete picture of all entries.

**Independent Test**: Can be fully tested by opening Entradas and verifying that one-off transactions and recurring-generated entries appear together in one list, ordered by date, with no tab bar present.

**Acceptance Scenarios**:

1. **Given** the Entradas section contains both one-off transactions and recurring-generated entries, **When** the user opens Entradas, **Then** all entries are shown in a single list ordered by date (most recent first), with no tab bar.
2. **Given** the unified list is displayed, **When** the user selects a time range filter, **Then** only entries within that date range are shown, regardless of entry type.
3. **Given** a list containing both entry types, **When** the user looks at any entry generated by a recurring template, **Then** that entry displays a visible recurrence indicator (e.g., a cycle/repeat icon or badge) that is absent on one-off entries.
4. **Given** no entries exist in the selected time range, **When** the view loads, **Then** a single empty-state message is shown.

---

### User Story 2 - Delete a Recurring Entry (Priority: P2)

The user taps the delete action on an entry that was generated by a recurring template. Because this action affects not just the individual entry but the entire future schedule, a confirmation dialog appears that clearly explains what will happen: the recurring template is cancelled (no new entries will be generated), while the entry the user is looking at — along with all previously generated entries from that template — remains in the list. The user can proceed or cancel.

**Why this priority**: Deleting a recurring entry has broader consequences than deleting a one-off transaction. Clear, explicit confirmation copy is critical to prevent accidental template cancellation.

**Independent Test**: Can be fully tested by adding a recurring template with at least one generated entry, triggering delete on that entry, and verifying the dialog text, the template cancellation, and the preservation of the individual entry.

**Acceptance Scenarios**:

1. **Given** a recurring entry is visible in the list, **When** the user initiates deletion, **Then** a confirmation dialog appears with explanatory text that states: (a) the recurring schedule will be cancelled, (b) no new entries will be generated, and (c) this entry and all previously generated entries are preserved.
2. **Given** the confirmation dialog is shown, **When** the user confirms, **Then** the recurring template is cancelled, no future entries will be generated, and the current entry remains visible in the list without a recurrence indicator.
3. **Given** the confirmation dialog is shown, **When** the user cancels, **Then** nothing changes — the template remains active and the entry remains in the list unchanged.
4. **Given** the user cancelled a template via a recurring entry deletion, **When** the list is viewed with a broader time range, **Then** all previously generated entries from that template are still present.

---

### User Story 3 - Delete a One-Off Transaction (Priority: P3)

The user taps the delete action on a one-off transaction. A confirmation dialog appears (same as existing behaviour). On confirmation, the single entry is permanently removed.

**Why this priority**: Existing behaviour that must be preserved unchanged in the new unified view. Lower priority because no new logic is required — only continuity verification.

**Independent Test**: Can be fully tested by adding a one-off transaction, triggering delete from the unified list, and verifying the entry is removed after confirmation.

**Acceptance Scenarios**:

1. **Given** a one-off transaction is visible in the list, **When** the user initiates deletion, **Then** a confirmation dialog appears asking to confirm permanent deletion of that single entry.
2. **Given** the confirmation dialog is shown, **When** the user confirms, **Then** the entry is permanently removed from the list.
3. **Given** the confirmation dialog is shown, **When** the user cancels, **Then** the entry remains in the list unchanged.

---

### Edge Cases

- What happens when a recurring template has generated entries but none fall within the currently selected time range? The user must widen the time range to reach an entry from that template before they can cancel it.
- What happens when a recurring entry's template has already been cancelled (orphaned entry)? The entry is displayed as a regular entry with no recurrence indicator.
- What if deletion of the recurring template fails (e.g., a storage error)? The confirmation dialog closes, the entry and template remain unchanged, and the user sees an error indication.
- What happens when the list contains only one entry type (e.g., no recurring entries exist)? The list renders normally with no recurrence indicators shown; the empty-state message is a single message covering all entry types.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The Entradas view MUST display all entries — both one-off transactions and entries generated by recurring templates — in a single chronological list (most recent first).
- **FR-002**: The Entradas view MUST NOT contain a tab bar; the existing "Transacciones" and "Recurrentes" tabs MUST be removed.
- **FR-003**: Each entry generated by an active recurring template MUST display a recurrence indicator (icon or badge) that is visually distinct and absent from one-off entries. The entry row layout is otherwise identical to a one-off entry row — no additional template metadata (periodicity, end date) is shown.
- **FR-004**: The unified list MUST support time range filtering, consistent with the existing filter behaviour on the former Transacciones tab.
- **FR-005**: Each entry in the list MUST provide a delete action regardless of its type (one-off or recurring).
- **FR-006**: Deleting a one-off transaction MUST show a confirmation dialog and, on confirmation, permanently remove only that entry.
- **FR-007**: Deleting a recurring entry MUST show a confirmation dialog with explanatory text that covers all three consequences: (a) the recurring schedule will be cancelled, (b) no new entries will be generated, and (c) this entry and all previously generated entries are preserved.
- **FR-008**: On confirmation of a recurring entry deletion, the system MUST cancel the associated recurring template while leaving the individual entry and all previously generated entries intact.
- **FR-009**: After a recurring template is cancelled via entry deletion, ALL entries from that template visible in the current list view MUST immediately update to remove the recurrence indicator — without requiring navigation away and back.
- **FR-010**: On cancellation of any confirmation dialog, the system MUST leave all data unchanged.

### Key Entities

- **Entry**: A single financial event (income or expense) recorded for a specific date. May be created manually (one-off) or generated automatically by a recurring template. Carries an optional reference to its originating template.
- **Recurring Template**: A schedule definition that generates entries at a regular cadence. Can be active (generating entries) or cancelled (no longer generating). Cancellation does not delete previously generated entries.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Users can view all their financial entries — one-off and recurring — in a single screen without switching tabs or sections.
- **SC-002**: Users can visually distinguish recurring entries from one-off entries at a glance for every entry in the list.
- **SC-003**: Every confirmation dialog for a recurring entry deletion explicitly names all three consequences (schedule cancelled, no future entries, existing entries preserved) before the user can confirm.
- **SC-004**: All previously generated entries from a cancelled recurring template remain accessible in the list after cancellation.
- **SC-005**: One-off transaction deletion continues to work with the same number of interaction steps as before this change (open confirmation → confirm).

## Clarifications

### Session 2026-04-12

- Q: Do recurring entry rows show template metadata (periodicity, end date) beyond the recurrence icon? → A: Icon/badge only — row layout is otherwise identical to one-off entries; no template metadata shown on the row.
- Q: After cancelling a template via entry deletion, do sibling entries from that template immediately lose their recurrence indicator in the current view? → A: Yes — all entries from the cancelled template immediately update in the current list view without requiring navigation.

## Assumptions

- The time range filter previously available only on the Transacciones tab is carried forward to the unified list as-is, with no changes to the available range options.
- All entries generated by a recurring template are already stored as individual transaction records; no changes to the generation logic are in scope.
- "Conservar la entrada individual" means the entry remains as a persisted record in the list — it is not removed when its originating template is cancelled.
- Entries whose template has been cancelled are displayed without a recurrence indicator, as the template reference is no longer active.
- The recurrence indicator is purely visual (icon or badge); no additional interaction from the indicator itself (e.g., tapping the badge to view template details) is in scope for this feature.
- Entries are shown most-recent-first within the selected time range, consistent with existing transaction list conventions.
- The empty-state experience for the unified list is a single message covering all entry types — no per-type empty states.
